# robocode 0.6.0: design

**Status:** approved, 2026-11-17. Revised from the draft in `_wb/v0.6.0_design.md` (written from `master` at
`8b27f3e`, crate 0.5.0). This file is the source of truth from here on; the `_wb` draft is not kept in sync.
**Base branch:** `v0.6.0`, branched from `fuzz-drift`.
**Why now:** RoboCheck (labs.cryptopatrick.com/robocheck/) runs on robocode 0.5.0. Its next rules and its page
need four things the engine can't do yet. RoboCheck's own changes for 0.6.0 are a separate plan in the site repo.

## What 0.6.0 adds

1. **Battlefield ratios:** 4:3, 2:1, 16:9 and 1:1, each with an urban map that fits it.
2. **Buildings block the radar:** a robot can't see another robot through a building.
3. **The radar beam is drawn as it is blocked:** the viewers show what the radar actually swept, cut off by buildings.
4. **Maneuvers and risk profiles:** a library of five maneuvers (search, patrol, defensive, evade, attack) and
   three risk profiles (cautious, normal, aggressive), a robot that chooses between them every turn, and the
   choice recorded and shown in the viewer.

## Goals

- Each feature is useful on its own in robocode, and not only for RoboCheck.
- **Battles stay deterministic.** The same robots, arena and seed give the same recording, byte for byte.
- **0.5.0 battles stay reproducible.** An open-arena 4:3 battle (800 × 600, no buildings) between 0.5.0 robots gives
  a recording identical to 0.5.0's, apart from the version fields. Radar blocking only changes battles with
  buildings, and ratios only add sizes.
- The viewers (2D and 3D, `web/`) show all four features.

## Non-goals

- No new robot senses beyond what the radar gives. There are no bullet sightings, no hit or wall events and no
  building map in `Observation`. Maneuvers work from what a robot can sense.
- No changes to physics constants (speeds, turn rates, damage, gun heat, radar range).
- No user-designed maps. Each ratio has one fixed urban map.
- No equal-area ratio sizes. 0.6.0 uses equal height; equal-area (or other) sizes are a candidate for 0.6.5.
- No Verus proofs of the maneuvers in 0.6.0 (see "Verus" below for what stays verifiable).
- No changes to the Arena or profile-language roadmap item, though maneuvers are designed so they can become its
  states later.

## Anti-goals (failure even if it works)

- **A beam drawing that disagrees with the engine.** If the viewer shows a scanned robot outside the beam, the
  drawing is lying. The drawn beam and the scan must come from the same geometry.
- **Silently changed 0.5.0 results:** for example a 4:3 urban map that moves a building, or a scan rule that changes
  open-arena battles.
- **Randomness that isn't seeded.** Maneuvers that use `rand` or wall-clock time would make recordings
  unreproducible.

## 1. Battlefield ratios

### Sizes

**Equal height.** Every ratio is 600 px high:

| Ratio | Size (px) |
|---|---|
| 4:3 | 800 × 600 |
| 2:1 | 1200 × 600 |
| 16:9 | 1067 × 600 (not exact) |
| 1:1 | 600 × 600 |

This keeps robots the same size on screen at the same zoom. The cost is that wide arenas give longer battles.
Alternative sizes (such as equal area) may come in 0.6.5.

A ratio is a preset size; `Battlefield::new(w, h)` with any size in 400..=5000 still works.

### API

- `pub enum Ratio { R4x3, R2x1, R16x9, R1x1 }` next to `Battlefield`, with `Ratio::size(self) -> (f64, f64)`,
  `Ratio::name(self) -> &'static str` ("4:3" and so on) and `FromStr` for "4:3", "2:1", "16:9" and "1:1".
- `Battlefield::from_ratio(Ratio)`. `BattleConfig::default()` stays 4:3, 800 × 600.
- The CLI gets `cargo robocode battle --ratio 16:9` (conflicts with explicit `--width`/`--height`). The wasm `record`
  entry gets an optional ratio, and the web New Battle form gets a ratio picker.

### Urban maps

Today's `Terrain::urban(w, h)` (`src/terrain.rs`) places buildings at absolute 800 × 600 positions and drops the
ones that don't fit. In 0.6.0:

- **4:3 at 800 × 600 must give exactly today's terrain.** Test: compare it rectangle for rectangle with a table
  copied from 0.5.0.
- The other ratios each get a map laid out by the same rules: roads cross at the centre, four blocks of buildings,
  spawn corners clear, and no building closer than 40 px to a wall, so that tanks can pass. Building *positions*
  scale with the arena, but building *sizes* don't stretch (a 2:1 map has more or wider-spaced blocks, not
  wide flat buildings).
- Each map is a fixed table in the source code, not generated at run time, so a map can only change in a commit
  that someone reviews.
- Any other size keeps today's behaviour (the 800 × 600 map's buildings that fit), so existing callers don't break.
- Test, for each ratio: every spawn point is clear of every building grown by the robot radius, and every building
  is inside the field.

### Viewers

`draw.ts` already takes its size from `rec.battlefield`. Check that the 2D canvas, its labels (`labelX`,
`labelY`) and the 3D scene's camera framing all fit each ratio, with a test for each ratio (the canvas size matches
the field, and the 3D camera keeps all four walls in view).

## 2. Buildings block the radar

### The rule

In 0.5.0, robot A scans robot B when B is within `RADAR_SCAN_RADIUS` (1200 px) and B's body (a circle of
`ROBOT_RADIUS`) overlaps the arc A's radar swept this turn. 0.6.0 adds one more condition, the **centre-line rule**:

> **A scans B only if the straight line from A's centre to B's centre crosses no building.**

- "Crosses" means the segment touches a building's rectangle anywhere, edges and corners included. A line that
  only grazes a corner counts as blocked. This is the conservative choice: when in doubt, the robot doesn't see.
- Use the same segment-rectangle geometry that bullets already use (`Rect::first_contact` in `src/geometry.rs`,
  which the bullet code in `engine.rs` uses to absorb bullets), so that bullets and radar can't disagree about what
  a building is. This is the **shared line-of-sight function**: one function, used by the scan rule and by
  `radar_beam`.
- Robots don't block the radar, only buildings. (Java Robocode has no occlusion at all, so this is our rule.)
- The body-visible rule (B is scanned if any part of its body is in line of sight) was considered and rejected
  as too complicated for 0.6.0.

### Consequences to state in the docs

- A target's `age` now grows while it hides behind a building, so "scanned this turn" (`age == 0`) also means "in
  line of sight at the end of last turn". RoboCheck's rule S2 gets this for free.
- Bullets still fly in straight lines and buildings still absorb them. A robot can still fire at a remembered
  position that is now behind a building, and the shot hits the building.

### Tests

- A unit test in the engine: two robots facing each other with a building between them scan nothing. Remove
  the building, and both scan.
- Grazing: a line that just touches a building's corner is blocked.
- Open arena: a recorded 0.5.0 open-arena battle replays identically (this is the reproducibility goal above).

## 3. The radar beam drawn as it is blocked

### What gets drawn

Today the 2D viewer draws the swept arc as a 1200 px wedge (`draw.ts`, `scanArcs`). In 0.6.0 the wedge is
**cut off at the first building on each ray**: inside the sweep, the beam is the visibility polygon from the robot's
centre, clipped to the scan radius and the field walls. A building in the sweep leaves a dark "shadow" behind it.

### One geometry, two users

To meet the anti-goal (the drawing must not lie), the beam polygon is computed in Rust, next to the scan rule, and
**recorded**. The viewer doesn't recompute it.

- `pub fn radar_beam(origin: Point, from_heading: f64, sweep: f64, buildings: &[Rect], field: &Battlefield)
  -> Vec<Point>`: the polygon of the swept region that the radar can see from `origin`, in battlefield pixels.
  It uses the shared line-of-sight function from §2.
- The beam is a polygon, not an arc. Rays are cast at four kinds of event, each at the event's angle and at ±1e-5 rad:
  - the vertices of the target region T (which include the outer edge, at most every 2°);
  - building corners strictly inside T;
  - building edges crossing T's boundary;
  - building edges crossing each other (where the nearest boundary switches).

  Clean-up: vertices closer than 1e-7 px are merged, and collinear vertices are merged.
- **The polygon is widened so that it never under-draws.** A robot is scanned when any part of its body overlaps
  the sweep, so its centre can sit just outside the swept angle or range. So:
  - the polygon's angular extent is widened on each side by the angle `ROBOT_RADIUS` subtends, and its range
    by `ROBOT_RADIUS` (to `RADAR_SCAN_RADIUS + ROBOT_RADIUS`);
  - the outer edge is drawn *outside* the arc, never inside it: each 2° segment lies on or beyond the circle
    (for example, vertices at `r / cos(θ/2)` so the chords are tangent to the circle), so that straight edges
    never cut corners off the region they stand for.

### Tests

- **Line of sight (exact):** for random robots and buildings, the scan rule's line-of-sight result equals the
  shared line-of-sight function's result for the centre-to-centre segment. This is the test that pins the rule.
- **Drawing (looser):** for random robots and buildings, every robot that is scanned has its centre inside the
  scanner's widened beam polygon, or within 0.5 px of its edge (the recording rounds to 0.1 px, and rays next to
  a building corner are cast a tiny angle either side of it). The converse is not required: the widened polygon
  may contain centres that were not scanned.

### Recording

- The recording format goes to **version 2**. In recording version 2, each robot's frame for each turn gets a new
  `beam` entry: the corner points of the area its radar actually swept, cut off by buildings, as
  `[[x, y], ...]`, with coordinates rounded to 0.1 px. A radar that didn't move still scans along a line (0.5.0
  rule), so its beam is the thin widened line, not empty. A dead robot's beam is empty.
- In a battle with no buildings, such as the open arena, nothing can block the radar, so the beam is always the
  plain wedge the viewer already draws from the radar headings.
- In that case the recording leaves `beam` out of every frame, and the viewer draws the wedge as it does for
  version 1 recordings. Writing hundreds of polygon points per turn that the viewer could work out itself would
  only make the file bigger.
- This also keeps open-arena recordings almost unchanged from 0.5.0, which helps the goal that old battles
  reproduce.
- The viewers read versions 1 and 2. A version 1 recording draws the plain wedge.
- **Size check:** the stored RoboCheck urban recordings must not grow by more than 50% (they average about 40 kB
  each, gzipped). If they do, record the beam only every Nth turn, or only while the radar is moving.

### Viewers

- 2D: fill the polygon with today's arc style. Draw the shadow behind a building in a darker tint if the graphic
  identity allows it, or leave it undrawn.
- 3D: skips the beam in 0.6.0; say so in `docs/viewer.md`. A translucent fan mesh from the recorded polygon, at
  radar height, can come later.

## 4. Maneuvers and risk profiles

### Where they live

- A new module, `robocode::strategy::maneuver`, is a library that any robot can use. It is not a change to the
  engine. `Strategy` stays `decide(&mut self, &Observation) -> Action`.
- A new built-in robot, `robots::Tactician`, picks a maneuver every turn and has a fixed risk profile. It is the
  reference robot that shows all of this, and it's the opponent RoboCheck will use.
- Maneuvers produce plain `Action`s. Anything that checks Actions (Verus contracts, RoboCheck's specs and its
  violation finder) keeps working unchanged, because it sees the same Action type.

### Types

```rust
pub enum Maneuver { Search, Patrol, Defensive, Evade, Attack }
pub enum Risk { Cautious, Normal, Aggressive }
pub struct Intent { pub maneuver: Maneuver, pub risk: Risk }
```

- `Strategy` gains `fn intent(&self) -> Option<Intent> { None }`, a default method, so existing robots compile
  unchanged. The runner reads it after `decide` each turn and records it.

### The maneuvers

Each one is a function with the same shape, `fn(&Observation, &mut ManeuverMemory, &RiskParams) -> Action`.
`ManeuverMemory` is small, fixed-size state the robot owns: a patrol waypoint index, the last seen target energy,
the robot's own energy last turn, the target's last position and speed, the evade direction, turns spent in the
current maneuver, and a seeded RNG state. Every maneuver turns the radar, so that a robot never goes blind.

| Maneuver | When it suits | What it does |
|---|---|---|
| **Search** | no target, or the target is stale (`age` > the risk's stale limit) | radar spins at full speed; drives toward the field centre, then in widening loops; gun follows the radar |
| **Patrol** | no target seen for a while, energy healthy | drives a fixed loop of waypoints inset from the walls (along the roads on urban maps); radar sweeps ahead |
| **Defensive** | target known, own energy below the risk's reserve | stays put or backs off to keep distance, keeps the body side-on to the target, keeps the radar locked; fires only aimed, low-power shots |
| **Evade** | a shot was detected (see below) | drives perpendicular to the target's bearing for a set number of turns, and changes direction on a seeded coin flip |
| **Attack** | target fresh, own energy above the reserve | closes to the risk's engagement distance, keeps the radar locked, aims the gun and fires when aimed |

### Shot detection

The only bullet information a robot can get is the target's energy: a target that fires loses its bullet's power
(0.1 to 3.0). The docs must say so. `Observation` has no hit or wall events, and several other things also drop
a target's energy by 0.1 to 3.0:

- a low-power hit by the robot's own bullet (4 × power for powers up to 1.0, so a power 0.1–0.75 bullet takes off
  0.4–3.0);
- the target driving into a wall (1.0 to 5.0);
- the two robots colliding (0.6).

Evade detects a shot when, between two fresh scans (`age == 0` both times), the target's energy dropped by 0.1 to
3.0, **and** none of these explanations applies:

- **Own hit:** the robot's own energy rose by 3 × power since last turn (a bullet hit pays back three times its power).
  This rarely matters for Tactician, whose own shots are 1.0–3.0 power and take off 4.0–16.0, outside the range.
- **Wall:** the target was moving last time it was seen and is now stopped within `ROBOT_RADIUS` + 2 px of a wall.
- **Collision:** the target is within 2 × `ROBOT_RADIUS` (plus a small margin) of the robot.

**Known limit:** these are guesses from what the robot sees, so Evade still sometimes flinches when nothing was
fired, and can miss a shot fired in the same turn as a collision or wall hit. This is accepted. Adding hit and wall
events to `Observation` would fix it, but that changes the types Verus and RoboCheck depend on, and is out of
scope (see Non-goals).

### How Tactician chooses

Tactician chooses by a fixed priority, top first, and switches at most once every 8 turns (hysteresis), except
that Evade can interrupt any other maneuver:

1. **Evade** if a shot was just detected and the risk allows evading (Aggressive evades only when below its reserve).
2. **Search** if there's no target or it's stale.
3. **Defensive** if own energy is below the risk's reserve.
4. **Attack** if the target is fresh.
5. **Patrol** otherwise.

### Risk profiles

A risk profile is a set of parameters, `RiskParams`, that every maneuver reads. These are starting values. They are
not tuned before release; tuning by running battles can come later. Energy is stored in thousandths as `units::Energy(u32)`; the table gives each
value both ways.

| Parameter | Cautious | Normal | Aggressive |
|---|---|---|---|
| energy reserve: below it, go Defensive | 40.0 (`Energy(40000)`) | 20.0 (`Energy(20000)`) | 5.0 (`Energy(5000)`) |
| engagement distance (px) | 450 | 300 | 150 |
| fire only when aimed within | 2° | 4° | 8° |
| shot power | 1.0 (`Energy(1000)`) | 2.0 (`Energy(2000)`) | 3.0 (`Energy(3000)`) |
| keep from walls and buildings (px) | 80 | 50 | 25 |
| evade length (turns) | 20 | 12 | 6 |
| target is stale after (turns) | 10 | 20 | 30 |

- The **fire filter** applies whatever the profile. No maneuver fires without a fresh target (`age == 0`), or with
  a shot it can't afford (power below its energy). This mirrors `SafeShooter`'s `ready`. A risk profile changes
  how much a robot risks, not whether it shoots at nothing.

### Recording and viewer

- Recording version 2 (the same bump as the beam) adds `intent: {"maneuver": "attack", "risk": "normal"}` to a
  robot's frame when `intent()` returns one. It is left out otherwise, so 0.5.0 robots' frames don't change.
- The 2D viewer shows it under the robot's name label (for example "ATTACK · normal", in mono). The robot panel
  shows the current maneuver and how long it has run.
- Colours follow the graphic identity: no new colour per maneuver. It is text only.

### Tests

- Each maneuver gets a unit test from a hand-made `Observation`. For example, Search with no target turns the radar
  by the full 45°, and Evade drives at right angles to the target's bearing.
- Shot detection gets a table test: one row per explanation (own hit, wall, collision) that must *not* trigger
  Evade, and a plain shot that must.
- Tactician's choice gets a table test, one row per priority rule, plus the hysteresis rule.
- Fire filter: a property test where, for random observations and every maneuver and risk, the Action never fires
  without `age == 0` and power below energy.
- Determinism: two Tactician battles with the same seed give identical recordings.

## Verus

- The engine changes (ratios, radar blocking, beam) are outside the Verus-checked code, as today's engine is.
- `Observation`, `Action` and `well_formed` don't change, so existing Verus contracts and RoboCheck's specs
  keep their meaning. `field_width` and `field_height` take the new sizes, all within `well_formed`'s bound.
- Stretch goal, not required: give the maneuver fire filter a Verus contract, `ensures r.fire is Some ==>
  (age == 0 && power < energy)`, as `SafeShooter` has today.

## Release

- Version **0.6.0**. Radar blocking changes urban battles, which is a behaviour change. 0.x allows that in a minor
  release; say so in the CHANGELOG (git-cliff).
- Docs: update `docs/robot-api.md` (Intent, maneuvers, shot detection and its limit), `docs/viewer.md` (beam,
  ratio, intent label) and `docs/architecture.md` (scan rule), and add a line to `README.md` per feature.
- Build order inside 0.6.0, each step releasable on its own: **(1) ratios and maps, (2) radar blocking and
  `radar_beam`, (3) recording v2 and the beam drawing, (4) maneuvers, risk and Tactician, (5) intent in the
  recording and viewer.**
- **Base branch:** `v0.6.0`, branched from `fuzz-drift` (which has five commits not yet on `master`: fuzz CI, the
  release-metadata test, the urban example, a docs commit and a fuzz target).

## What this means for RoboCheck (not part of this spec)

These are listed so that the robocode work doesn't paint RoboCheck into a corner. They go in a RoboCheck plan after
0.6.0 ships:

- The battle panel gets a ratio picker, and a wide ratio (2:1 or 16:9) fills the page like RailCheck's board.
- The opponent changes from Circler to Tactician, perhaps with a risk picker.
- The robot-writing prompt may ask the AI to use the maneuver library, which shows that a proof holds for every
  maneuver and risk.
- All stored runs are regenerated on 0.6.0 (about $0.30 per full set of 8).
- A line-of-fire rule (no firing into a building) is still a RoboCheck rule, measured in the robocheck crate as S3's
  clearance is. Radar blocking doesn't make it redundant, because a target scanned last turn can step behind a
  building.

## Decisions

Made in review (2026-11-17):

- Ratio sizes: **equal height** (600 px). Alternatives deferred to 0.6.5.
- Radar occlusion: **the centre-line rule**. Body-visible rejected as too complicated.
- Energy values are stored in thousandths (`Energy(u32)`), shown both ways in the risk table.
- Beam: widened polygon, outer edge outside the arc; exact test on line of sight, looser test on the drawing.
- Shot detection: no new senses; heuristics for own hits, walls and collisions; false flinches are a known limit.
- The 3D view skips the beam in 0.6.0.
- Risk parameters ship with the starting values; no tuning before release.
- Base branch: `v0.6.0` from `fuzz-drift`.

## Calls made (check these)

- The ratio is a preset, not a new arena type, and any size still works.
- The beam polygon is computed in Rust and recorded, not recomputed by the viewer, so the drawing can't disagree with
  the engine.
- Maneuvers are a library plus one reference robot (Tactician), not engine behaviour, so `Strategy` stays
  as it is and nothing Verus checks changes.
- No new senses: Evade detects shots from the target's energy drop.

## Amendments (during implementation)

- **R5, beam size.** The beam is recorded in full on every turn, even when the radar is still. Urban recordings grow about
  61–78% gzipped, over the 50% budget. The user accepted this; compaction is left for later.
- **R8, Search and Patrol.** With no target seen, Tactician alternates Search and Patrol every 150 turns, so it can find
  an opponent hidden behind a building.
- **R9, Evade length.** Evade is held for the risk's `evade_turns`, not for Tactician's 8-turn hysteresis.
- **R10′, stuck recovery.** After 3 turns at velocity 0 following a move command, recovery issues a single back-off (60
  px, against the stuck direction) and a ±90° turn, then leaves movement to the engine for the rest of its 10 turns.
- **R11 and R11′, wall guard.** Every maneuver, Defensive included, has its `ahead` clipped so the robot stays 30 px from
  a wall. Defensive is exempt only from stuck recovery. A recovery back-off needs at least 10 px of room.
- **Search** orbits at a fixed radius around the centre instead of driving in widening loops.
- **Evade sides.** The coin picks bearing +90° or −90° and the robot drives forward, so the two outcomes travel in
  opposite directions. When the chosen side has less than 30 px of wall room, Evade takes the other side.
