# Robot API Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A developer-facing Robot API in the `robocode` crate, modelled on Java's `AdvancedRobot`, so people can write their own robots in a single file. This is project 1 of 4: Robot API → upload and compile `robot.rs` → per-robot WebAssembly sandbox → viewer integration.

**Architecture:** New module `robocode::api`. A robot implements `trait Robot`. Each turn the runner delivers events to its handlers (`on_scanned_robot`, `on_hit_by_bullet`, …), then calls `run`. Every handler gets the robot's `Status` and a `Commands` buffer of `set_*` calls, applied when the turn executes, as with `AdvancedRobot::execute()`. Units are Java's: `f64` pixels and degrees. The runner drives `Box<dyn Robot>`. The existing fixed-point `Strategy` robots, including the Verus-proved SafeShooter, keep working through `StrategyRobot`, an adapter that rebuilds the exact `Observation` the runner builds today.

**Tech Stack:** Rust (no new dependencies).

**Spec:** No separate design doc; the user opted out of questions ("proceed"). The authority is the conversation: the Java Robot API at `_wb/latest_version_robocode-main/robocode.api` and the four-project breakdown above. Rulings are provisional.

## Design

```rust
// robocode::api
pub struct Status {                // this robot, at the start of the turn
    pub time: u64, pub name: String, pub others: usize,
    pub x: f64, pub y: f64, pub energy: f64, pub velocity: f64, pub gun_heat: f64,
    pub heading: f64, pub gun_heading: f64, pub radar_heading: f64,            // degrees, 0 = up, clockwise
    pub distance_remaining: f64, pub turn_remaining: f64,
    pub gun_turn_remaining: f64, pub radar_turn_remaining: f64,
    pub battlefield_width: f64, pub battlefield_height: f64, pub gun_cooling_rate: f64,
}
pub enum Event {                   // from the previous turn, in this order
    ScannedRobot(ScannedRobotEvent), HitByBullet(HitByBulletEvent), BulletHit(BulletHitEvent),
    BulletMissed(BulletMissedEvent), HitWall(HitWallEvent), RobotDeath(RobotDeathEvent),
}
pub struct ScannedRobotEvent { pub name: String, pub bearing: f64 /* relative to own heading, (-180,180] */,
    pub absolute_bearing: f64, pub distance: f64, pub energy: f64, pub heading: f64, pub velocity: f64 }
pub struct HitByBulletEvent  { pub name: String /* shooter */, pub bearing: f64 /* relative */, pub power: f64 }
pub struct BulletHitEvent    { pub name: String /* victim */, pub energy: f64 /* victim's energy after the hit */, pub power: f64 }
pub struct BulletMissedEvent { pub power: f64 }
pub struct HitWallEvent      { pub bearing: f64 /* relative bearing to the wall */ }
pub struct RobotDeathEvent   { pub name: String }

#[derive(Default)] pub struct Commands { /* Option fields */ }
impl Commands {
    pub fn set_ahead(&mut self, px: f64); pub fn set_back(&mut self, px: f64);
    pub fn set_turn_right(&mut self, deg: f64); pub fn set_turn_left(&mut self, deg: f64);
    pub fn set_turn_gun_right(&mut self, deg: f64); pub fn set_turn_gun_left(&mut self, deg: f64);
    pub fn set_turn_radar_right(&mut self, deg: f64); pub fn set_turn_radar_left(&mut self, deg: f64);
    pub fn set_fire(&mut self, power: f64);
}

pub trait Robot {
    fn name(&self) -> &str;
    fn run(&mut self, status: &Status, cmd: &mut Commands);           // every turn, after event handlers
    fn on_scanned_robot(&mut self, _e: &ScannedRobotEvent, _s: &Status, _c: &mut Commands) {}
    fn on_hit_by_bullet(&mut self, _e: &HitByBulletEvent, _s: &Status, _c: &mut Commands) {}
    fn on_bullet_hit(&mut self, _e: &BulletHitEvent, _s: &Status, _c: &mut Commands) {}
    fn on_bullet_missed(&mut self, _e: &BulletMissedEvent, _s: &Status, _c: &mut Commands) {}
    fn on_hit_wall(&mut self, _e: &HitWallEvent, _s: &Status, _c: &mut Commands) {}
    fn on_robot_death(&mut self, _e: &RobotDeathEvent, _s: &Status, _c: &mut Commands) {}
    fn last_decision(&self) -> Option<(Observation, Action)> { None }  // for the viewer; StrategyRobot fills it
}
```

**Semantics:**
- **Order each turn:** handlers in `Event` enum order (scans sorted nearest first), then `run`, then the commands are applied. A later `set_*` of the same kind overwrites an earlier one. Kinds that are never set keep their pending value, like Java.
- **`set_back(px)`** is `set_ahead(-px)`, and `*_left(d)` is `*_right(-d)`.
- **Names come from `Robot::name()`.** Duplicates are numbered like Java: the 2nd `SittingDuck` becomes `SittingDuck (2)`, the 3rd `SittingDuck (3)`, while the first keeps its plain name.
- **Dead robots** get no calls.

**Not in this project:**
- the blocking `Robot` style (`ahead(100)` that waits);
- custom events;
- `onHitRobot` (the engine has no robot-robot collisions);
- `onWin` / `onDeath` / `onRoundEnded` (no rounds or scoring);
- teams;
- data files;
- colours;
- `onPaint`.

## Global Constraints

- `robocode` keeps zero non-optional dependencies. `cargo build` compiles no Verus crates, and `cargo build --features verus` works with plain cargo.
- **Regression gate:** SafeShooter vs Spinner (spawns `(100,100,0°)` and `(700,500,0°)`, 800×600) must still give exactly `winner=SafeShooter turns=386 energy=77.0/-1.0`. vs SittingDuck it must still give `turns=364 energy=147.0/0.0`. Pin both in a test **before** refactoring.
- Verus: `cargo verus verify --features verus` and `-p roboverus-solutions` stay at 0 errors. The exercises still fail only at their TODOs.
- The viewer keeps working: `cargo test -p robocode-wasm`, then `cd web && npm run wasm && npm test && npm run build`.
- Clippy `-D warnings` passes for the workspace and for `-p robocode` alone.
- Don't edit `README.md`, `LICENSE`, `COPYING` or `CONTRIBUTING.md`, or the user's `Cargo.toml` license line. Commits carry no Claude attribution. Work on branch `robot-api`.
- Java's sample robots are EPL and not ours to copy. Write new samples.

## Review Focus

1. **Wrap-around in relative bearings.** A scan straight behind is `180`, not `-180`. Relative bearings stay in `(-180, 180]`, and absolute bearings in `[0, 360)`. Tested in Task 3.
2. **Commands set several times in one turn.** Two `set_fire` calls in the same turn must still produce at most one bullet; the last call wins. Tested in Task 3.
3. **Duplicate robot names.** Two `SittingDuck`s are told apart in events. Tested in Task 3.
4. **Events about the dead.** A robot that died this turn gets no handlers and no `run`. Others get `RobotDeath` exactly once, and no further scans of it. Tested in Task 3.
5. **Missed bullets.** A bullet that leaves the field produces exactly one `BulletMissed` for its owner. One that hits produces none. Tested in Task 1.

### Task 3: Runner drives `Robot`; `StrategyRobot` adapter

**Files:**
- Modify: `src/runner.rs`, `src/api.rs`, `examples/battle.rs`, `wasm/src/lib.rs`, every `Battle::new` caller in `tests/`
- Test: `tests/api.rs`, `tests/runner.rs`

**Interfaces:**
- `Battle::new(config, spawns, robots: Vec<Box<dyn Robot>>)`.
- `pub struct StrategyRobot<S: Strategy>`, with `impl<S: Strategy> StrategyRobot<S> { pub fn new(s: S) -> Self }` and `impl Robot for StrategyRobot<S>`.
- `pub fn boxed<S: Strategy + 'static>(s: S) -> Box<dyn Robot>`, a convenience for `Box::new(StrategyRobot::new(s))`.
- **`StrategyRobot` keeps what `Battle::step` does today:**
  - it tracks the nearest scan of the turn and its age;
  - it forgets the target on its `RobotDeath`;
  - it builds the `Observation` with the same conversions as `runner::observe`, including the post-cooling gun heat;
  - it calls `decide`, turns the `Action` into commands, and records `last_decision`.
- `observe` and `apply` stay public for compatibility. `observe` may be re-expressed over `Status`.
- `Battle::last_decision(i)` returns `robots[i].last_decision()` if robot `i` acted this turn, otherwise `None`.
- `Battle::name(i)` returns the de-duplicated name.
